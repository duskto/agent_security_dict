## 六、G4 代码级证据链（按 commit `da7aa705` 逐段核验）

**① 输入 / 状态来源**
- `PUT /api/v4/access_control/policies` → `createAccessControlPolicy`；body 直接 `json.Decode` 成 `model.AccessControlPolicy`（`api4/access_control.go:46-50`），**`imports` / `scope` / `scope_id` 全部来自请求体**。
- 随后 `c.App.CreateOrUpdateAccessControlPolicy(...)`（`:164`）。

**② 校验逻辑（rc1 实际检查）**
- `type=parent`：非系统管理员需 `manage_team_access_rules`（`:83`）+ `ValidateTeamAdminPolicyOwnership(teamID, policy.ID)`（`:89`，仅当 `policy.ID != ""`）；且 **Scope/ScopeID 被强制改写**为 `(team, teamID)`（`:100-110`，注释：“never trust the body's scope fields”）。
- `type=channel`：非系统管理员需 `HasPermissionToChannel(user, policy.ID, manage_channel_access_rules)`（`:127`）+ `ValidateChannelAccessControlPolicyCreation`（`:134` → `app/access_control.go:2292-2305`，非系统管理员只允许 channel 类型）。
- `type=team`：非系统管理员需 `manage_team_access_rules`（`:146`）+ 自身包含性校验（`:152-157`）。
- `type=permission`：需要 `PermissionManageSystem`（`:112`）。

**③ 绕过条件（已闭合）**
- 模型层 v0.3（app 强制 `policy.Version = AccessControlPolicyVersionV0_3`，`app/access_control.go:108`）：
  - parent / permission 类型**禁止 Imports**（`model/access_policy.go:345-347`、`372-374`）；
  - **channel 与 team 类型允许 `imports`**（`:349-355`），v0.3 无数量上限。
- app 层 `CreateOrUpdateAccessControlPolicy`（`app/access_control.go:81-197`）**对 `Imports` 无任何校验**，直接交给 PAP：`acs.SavePolicy(rctx, policy)`（`:181`）。
- 而 `imports` 的「正规」写入路径是 assign/unassign：`AssignAccessControlPolicyToChannels()` 直接把 `child.Imports = [parentID]` 写进子策略（`app/access_control.go:1403+`，`1449` 处 `acs.SavePolicy(rctx, child)`）。
- assign 端点的门控（`api4/access_control.go:926-980`）：`channel_ids` + `team_id` 路径需 **team 级** `manage_team_access_rules` **且** `ValidateTeamAdminPolicyOwnership(teamID, parentPolicyID)`（要求被附加的 **parent 策略**归该 team：`app/team_access_control.go:164-196`）；`team_ids`（团队资源）路径需 **`PermissionManageSystem`**。
- **权限可得性（关键）**：`role.go` 中 **`channel_admin` 默认持有 `manage_channel_access_rules`**（`:1000`），**`team_admin` 持有 `manage_team_access_rules`（`:1072`）与 `manage_channel_access_rules`（`:1095`）**。
- ⇒ **rc1 中，仅具频道级 `manage_channel_access_rules` 的频道管理员即可经 upsert 端点提交 `type=channel, id=<自己频道>, imports=[<任意 parent 策略 ID>]`**，全程**没有**对 parent 策略的归属/作用域校验，也**不需要** team 级权限或系统权限 —— 即绕过了 assign 端点的所有权与层级门控。GA 的 `preserveSystemManagedFields` 正是把该字段固定回库中值来堵这条路。

**④ 调用方放行效果（部分闭合；量级未定）**
- `imports` 就是 ABAC 继承槽：parent 策略保存后会触发 `publishChannelPolicyEnforcedForChannelPoliciesWithImport(policy.ID)` / `publishTeamPolicyEnforcedForTeamPoliciesWithImport(...)`（`app/access_control.go:191-193`），并存在 `channelPolicyIDsWithImport` / `teamPolicyIDsWithImport`（`:1830-1892`）用于按导入关系重算生效范围；客户端动作亦由 `HydrateChannelPolicyActions`（`:1923`）按策略推导。
- ⇒ 「写入 `imports` 会改变该频道/团队实际适用的规则集合」这一点**已在代码路径上确认**，不需要再经 assign 端点（故本条**不能**按“必须再经 assign”直接否定）。
- **仍未闭合**：`PAP`（`a.Srv().ch.AccessControl` 的 `SavePolicy` 实现）**不在公开仓库**（`server/enterprise` 仅含 elasticsearch / message_export / metrics），无法排除 PAP 侧对 `imports` 的存在性/类型校验；且**具体收益取决于实例内既有 parent 策略及其规则内容**（需登录才能枚举）。因此**不得**表述为“已确认权限提升”，更不得表述为“已验证”。

**闭合所需最小证据（动态）**：一个持有 `manage_channel_access_rules` 的测试账号 + 一个由系统管理员创建的 parent 策略 ID；观察 `PUT /api/v4/access_control/policies`（`type=channel` + `imports=[<他人 parent>]`）是否返回 200 且该字段被持久化（对比 GA/11.10.2 应被固定回原值/拒绝）。
