## 三、根因（代码级，8.6.1 vs 8.6.2 对比）

`apps/meteor/server/modules/notifications/notifications.module.ts`：

```ts
// 8.6.1（本机运行版本）：对事件名 e 无白名单，直接转发给房间其他成员
this.streamRoomUsers.allowWrite(async function (eventName, ...args) {
    const [roomId, e] = eventName.split('/');            // e 来自调用方，运行时任意
    if (this.userId && (await Subscriptions.countByRoomIdAndUserId(roomId, this.userId)) > 0) {
        const subscriptions = await Subscriptions.findByRoomIdAndNotUserId(roomId, this.userId, {...}).toArray();
        subscriptions.forEach((s) => self.notifyUser(s.u._id, e, ...args));   // 转发副作用
    }
    return false;                                        // 仅抑制本流广播
});

// notifyUser: 直接 emit 到受害者的 notify-user 流
notifyUser(userId, eventName, ...args) { return this.streamUser.emit(`${userId}/${eventName}`, ...args); }
```

```diff
--- 8.6.1
+++ 8.6.2（补丁）

+    if (this.userId && ['video-conference','userData'].includes(e) &&
+        (await Subscriptions.countByRoomIdAndUserId(roomId, this.userId)) > 0) {
```

配套链路：

- `streamer.module.ts:244` 写入方法实现为 `if ((await isWriteAllowed(this, eventName, args)) !== true) return; __emit(...)`。
  即 `allowWrite` 回调（含上面的 `forEach notifyUser` **转发副作用**）先执行，`return false` 只跳过本流广播 —— 跨用户注入已发生。
- 流名映射 `subscriptionName = 'stream-' + name`（`streamer.module.ts:62`）：写入方法 `stream-notify-room-users`，订阅名 `stream-notify-user`。
- `streamUser.allowRead`（`notifications.module.ts:303`）：仅当 `this.userId === eventName.split('/')[0]` 才允许订阅，故受害者能且只能订阅自己的 `<userId>/...` 流。

## 四、复现结果：✅ 已复现（服务端注入本体）

方法：攻击者与受害者各自登录（普通用户），受害者建立 DDP 连接并按客户端默认行为订阅自身 `notify-user` 流；攻击者向 `stream-notify-room-users` 写入携带任意事件名的消息。

实测输出：

```
[对照] 受害者未加入房间时，攻击者注入 force_logout：
       受害者收到事件数 = 0  （countByRoomIdAndUserId 门控生效）
[+] 受害者加入频道: HTTP 200

[测试1] 攻击者写 '<roomId>/force_logout'：
       受害者收到 notify-user 事件: {"eventName": "iRntRT9wbxCanjKPg/force_logout", "args": []}

[测试2] 攻击者写任意事件名 '<roomId>/uiInteraction'（受害者另订阅该流）：

===== 结论 =====
对照(未同房间) 事件数: 0
测试1 force_logout 注入(同房间) 事件数: 1
测试2 uiInteraction 注入(同房间) 事件数: 1
```

要点：阴性对照（无房间关系）收 0 条，排除了“受害者本就能收到该事件”的保守解释；测试 2 证明**事件名与参数均无白名单**。

PoC：`poc.py`（凭据经环境变量传入，未硬编码口令）。

## 五、影响与边界

- **认证边界**：post-auth。任一**普通**认证用户即可，无需角色/特权。
- **前置条件**：攻击者与受害者同处一个房间（受害者可为任意房间成员）。攻击者自带建频道能力，且普通用户可 `channels.join` 公开频道，该前提可自主构造。
- **低权账号可达性**：目标开启**自助注册**（本次实测经 `POST /api/v1/users.register` 成功创建 2 个普通账号），故外部可自建低权账号；注册受每 IP 60s 限流。
- **权限结果**：攻击者向受害者 `notify-user` 流投递**任意事件名 + 调用方可控参数**，成功。
- **客户端影响（源码级确认，未端到端动态验证）**：8.6.1 `useForceLogout` 订阅 `${userId}/force_logout`，回调执行 `wipeLocalAuth()` 清本地登录态；`uiInteraction` 可渲染 UIKit 弹窗/横幅（UI 钓鱼）。**登出/钓鱼的实际端到端效果本轮未用真实客户端执行**，列为待验证。
- **影响性质**：本缺陷本质是“设计内的 fan-out 机制 + 缺失事件名授权校验”，非服务端 RCE；现实影响面受**受害者客户端实际订阅的事件名集合**约束（只有客户端本就监听的事件名才产生效果）。
