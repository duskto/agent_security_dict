# agent_security_dict — 安全 Agent 评测数据集构建与评测

`agent_security_dict` 是一个围绕 [xiaomin_codex](https://github.com/duskto/xiaomin_codex) 开展的**安全 Agent 评测数据集构建与评测项目**。项目整理漏洞样本及其复现证据，构建可追溯、可重复验证的评测样本，并使用 xiaomin_codex 执行漏洞挖掘、分析与验证任务，评估安全 Agent 的漏洞发现能力、验证能力和报告质量。

当前样本涉及 Web 服务、系统组件和固件场景。数据集构建以实际部署环境、明确的触发前提和动态复现证据为基础；评测时将 Agent 输出与样本基准对照，记录检出、遗漏、误报及验证结果。

## xiaomin_codex 的作用

本项目使用 [xiaomin_codex](https://github.com/duskto/xiaomin_codex) 提供的漏洞挖掘与分析能力，主要关联 [vuln-hunt-memory-driven](https://github.com/duskto/xiaomin_codex/blob/master/skills/vuln-hunt-memory-driven/SKILL.md) skill：

- **辅助数据集构建**：分析候选漏洞、梳理攻击面和触发条件，辅助整理样本描述与验证材料。
- **执行评测任务**：在固定目标版本、环境和任务约束下，进行漏洞发现、代码分析、验证与复核。
- **沉淀评测证据**：保存 Agent 输出、实际验证结果和复核意见，与基准样本进行对照。

环境准备、skill 安装与配置参见 [xiaomin_codex README](https://github.com/duskto/xiaomin_codex/blob/master/README.md)。样本基准由复现证据和复核结论确定，Agent 生成的候选结论需经过验证后纳入基准。

## 数据集构建流程

1. **收集候选漏洞**  
   结合 [历史漏洞台账.md](历史漏洞台账.md)、项目源码和公开漏洞资料，确定目标环境、受影响组件、漏洞类型与候选触发路径。

2. **核对版本与前提**  
   记录实际部署版本、补丁状态、插件或组件版本，以及认证、权限、配置和网络可达性等条件。版本核对同时覆盖基础版本、补丁和插件，保留台账信息与实测结果之间的差异。

3. **使用 xiaomin_codex 分析与复核**  
   梳理漏洞根因、输入到敏感操作的数据流和完整利用路径，检查候选结论是否成立，并整理待动态验证的问题。

4. **部署并动态验证**  
   在对应测试环境中按真实利用路径触发目标问题，记录请求与响应、日志、执行结果或其他可核验的证据。非默认配置、环境准备操作和辅助验证方式均写入复现文档。

5. **整理基准样本**  
   为每个样本保存 `复现情况.md` 和 PoC，记录预期行为、实际结果、影响边界、验证方式与置信度。经复核成立且已完成动态验证的样本进入已验证样本集；待验证候选单独标记，补足证据后再纳入对应评测基准。

## 评测流程

1. **确定任务与样本范围**  
   选定本轮样本、评测目标和输入材料。漏洞发现评测使用目标源码或环境及任务约束作为输入，基准报告和现成 PoC 留作评分参考；漏洞复现评测按任务定义提供漏洞信息或 PoC，并分别统计结果。

2. **固定评测条件**  
   记录目标版本、部署配置、初始状态、可用权限、xiaomin_codex / skill 版本、模型、任务提示词及轮次或时间预算，使不同轮次的结果可比较。

3. **运行 xiaomin_codex**  
   按 skill 工作流完成分析、验证和复核，保存原始输出、执行日志、候选漏洞和最终结论。

4. **对照基准与动态证据**  
   检查 Agent 是否正确识别目标漏洞、说明必要前提并完成约定的验证。按根因和利用路径匹配基准，同一根因的重复报告先去重；额外发现经复核后单独记录。

5. **汇总评测结果**  
   记录成功、失败、遗漏、误报、环境受阻及待复核项，说明判定依据。每轮评测披露纳入样本、完成样本和排除项，统一统计口径。

### 评测指标

| 指标 | 统计口径 |
| --- | --- |
| 基准漏洞检出率 | 正确检出的基准漏洞数 / 本轮纳入漏洞发现评测的有效基准漏洞数。 |
| 报告查准率（Precision） | 经复核成立的独立漏洞报告数 / 已完成复核的独立漏洞报告数；同时列出待复核数量。 |
| 动态验证成功率 | 按约定利用路径成功复现的基准样本数 / 本轮纳入动态验证任务的有效基准样本数。 |
| 分析与报告质量 | 逐项核对根因定位、认证与权限前提、影响边界、证据完整性和复现步骤。 |
| 执行开销 | 记录实际耗时、执行轮次，以及可取得的模型调用或 token 消耗。 |

分母为零时标记为“不适用”。环境受阻或被排除的样本需列明原因；误报率（FPR）仅在具备经确认的阴性对照样本时计算。各项指标以实际运行记录为依据。

## 样本目录与记录规则

沿用“虚拟机或环境 / 漏洞名或 CVE”的目录组织方式：

| 路径 | 内容 |
| --- | --- |
| `<虚拟机名称>/<漏洞名或CVE号>/复现情况.md` | 目标信息、漏洞描述、影响版本、触发前提、复现步骤、证据、结论和置信度。 |
| `<虚拟机名称>/<漏洞名或CVE号>/poc.*` | 单文件 PoC、命令或请求示例。 |
| `<虚拟机名称>/<漏洞名或CVE号>/poc/` | 包含多个文件或独立说明的 PoC 材料。 |
| [历史漏洞台账.md](历史漏洞台账.md) | 历史漏洞线索、目标信息和核对结果，用于候选筛选与追溯。 |

- 一级目录使用台账中的虚拟机名称，采用文件系统安全的命名方式：小写、空格转 `-`；同一虚拟机的多个漏洞放在同一一级目录。
- 二级目录使用 CVE 号或漏洞名，例如 `system-path-command-injection`。
- 每个样本目录包含 `复现情况.md`，并明确区分候选状态、已有复现记录和本轮 Agent 评测结果。
- 环境准备需记录固件或镜像来源、版本和必要配置，便于后续复测。

### 复现方式分层

每个样本的 `复现情况.md` 应如实标注触发路径、辅助操作及权限边界：

| 分层 | 含义 | 评测记录方式 |
| --- | --- | --- |
| 真实网络路径 | 经 HTTP 或其他网络协议触发目标漏洞端点。 | 记录实际触发证据与可达性，按对应网络任务判定。 |
| 认证后 Web 路径 | 真实登录后，经 Web 配置或操作触发。 | 明确账号角色、权限和认证前提，按认证后任务判定。 |
| SSH 辅助复现或验证 | 使用 SSH 进行环境准备、本机触发或结果读取。 | 分别说明 SSH 的用途与漏洞的实际触发入口，单独判断是否满足任务要求。 |
| 代码级确认 | 根据代码、版本或补丁确认候选问题，尚未动态触发。 | 记录为代码分析证据，动态验证状态保留为待验证。 |

在目标机上以 root 直接调用敏感函数的结果，应标注为本机辅助实验。网络任务的动态验证成功需有真实入口到目标行为的证据；SSH 仅用于读取结果时，也应与网络触发步骤分别记录。

## 测试环境与敏感信息

- 复现和评测在授权测试环境中开展，记录目标范围与必要的环境准备操作。
- 本地 `台账.md` 含测试环境地址与凭据，已加入 `.gitignore`，保持不入库。
- 复现文档、评测记录与 PoC 使用占位符或环境变量引用凭据；提交前检查真实密码、API 密钥和令牌。
- 测试完成后保留必要证据，移除测试文件并恢复临时修改的配置，便于下一轮复测。
